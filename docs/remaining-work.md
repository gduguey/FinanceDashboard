# Remaining work after the five-PR refactor

The five-PR VISION refactor landed as `v1.2.0` … `v1.7.0`. This is the triaged
backlog that came out of it: the entries in `known-gaps.md`, plus a repo-wide
audit, each one decided rather than left open. Item ids are stable — cite them
in branch names, commits and PR descriptions.

`KEPT` items are planned. `DROPPED` items were considered and consciously
declined, with the reason recorded so nobody re-opens them from an audit
document six months from now.

Two rules for anyone working this list:

**Version bumps follow the policy, not the previous PR.** `PATCH` for anything
whose user-visible behaviour does not change on purpose — which most of this
list is; `MINOR` only for something additive; `MAJOR` only when deploying needs
manual intervention beyond `git pull` and a restart. Say in the commit body
which rule applied. (The policy itself is at `docs/versioning.md`.)

**Check whether it is already handled before building anything.** Read the
neighbouring modules and their docstrings first. A1 and A3c on this list were
both queued as real bugs and both withdrawn on exactly that basis: the machinery
already existed one module over. Docstrings count as documentation. If you
conclude something is broken, state what you checked that would have covered it
and did not.

| A3b | Historical FX converted at today's rate | **DONE** (PR B) — `exchange_rates.smoothed_rate_series` evaluates the same trailing 30-day mean on every calendar day, and `ledger.currency.with_converted_amount` joins each row to its own date's rate. | A3c | Card refund counts as income | **DROPPED** — not a gap. `dashboard.income_statement.real_income_expense_legs` already excludes any transaction marked a transfer, manually or by a `TransferRule`. | A3d | `signColor` paints exactly zero green | **DONE** (PR B) — zero and `-0` both return the neutral colour. All twenty call sites audited: the four that negate their argument do so because growth is the bad direction there, and none relied on zero being green. The three inline `>= 0 ? '+'` prefixes moved with it. |
| A3e | "Alpha vs HYSA" labels two different quantities, neither of which is alpha | **DONE** (PR B) — now `excess_value_vs_hysa_usd` and `excess_return_vs_hysa_pct`, renamed through the API and the generated client so the word survives nowhere. | A3f | The contribution gate silently dropped every non-USD row | **DONE** (PR B) — found while closing A3a. Three of the four callers of `unallocated_balance` passed no `DisplayCurrency`, so the default `{"USD": 1.0}` left-joined a EUR posting or contribution to a null rate, nulled its amount, and `sum` skipped it: the figure refusing a contribution disagreed with the one `GET /goals/summary` displayed. `all_goal_balances` in the withdrawal path had the same defect against the shortfall it is compared with. |
| A4a | Automation reorder can lose a concurrent write | **DROPPED** — one user, two tabs, a deliberate drag in both at once. The consequence is a reorder that visibly does not stick, and is retried. Not worth a lock. |
| A4b | Target-allocation save can lose a concurrent write | **DONE** (PR F) — `dashboard.merge_target_allocation` is one `INSERT ... ON CONFLICT DO UPDATE` setting `target_allocation_pct \|\| :assignments - :removals`, so two patches of different symbols compose by construction: `ON CONFLICT DO UPDATE` re-reads the row it updates, and the second merge lands on the first's committed value. No version column, as recorded — a version would have made the two *conflict* and 409 one of them, which is a worse answer than merging. One correction to the entry: `self_group()` around the concatenation is required, because Postgres binds binary `-` tighter than `\|\|` and the unparenthesised form applies the deletion to the incoming patch instead of the stored map, so a delete-only patch silently does nothing. Also closed a second, unrecorded effect: the handler used to rewrite all twelve columns of the settings row through `save_settings`, so a concurrent HYSA or timezone save was collateral. |
| A5 | Nothing tells a user their oldest figures were converted at a clamped rate | **KEPT** — raised by PR B, deliberately not built there. The rate cache holds two years, so any posting older than that converts at the oldest trailing mean on file (`ledger.currency.with_converted_amount`), which is documented in `currency-handling.md` and invisible on screen. Every other approximation in the app is labelled; this one should be too, probably as a note on an income statement whose window starts before the cache does. The alternative — widening the fetch window — is a data-acquisition change with its own cost and failure modes and would be its own item. |
| A6 | A recurring addition funds in one currency and is stored labelled another | **KEPT** — raised by CodeRabbit on PR B, pre-existing and deliberately not fixed there. `ledger.goal_automations.run_recurring_additions` takes the unallocated pool as a bare float (USD, see A3f) and returns bare floats; `api.routers.goals.post_run_recurring_additions` then persists each one with `currency=automation.currency or "USD"`. A `percent`/`remainder` rule on a EUR automation therefore stores a USD-derived amount labelled EUR, and every later conversion compounds the error. Fixing it is a decision about what currency the pool is denominated in, not a patch: either convert each funded amount into the automation's currency on the way out, or refuse a non-base-currency automation. |
| A7 | `with_converted_amount` turns an unknown currency into a null amount | **KEPT** — raised by CodeRabbit on PR B. Both the scalar and the per-date paths left-join their rate table, so a row whose currency is in neither becomes a null amount that every `sum` then skips — the same silent-drop shape A3f existed to remove. It cannot happen through the API today, because the rate table is built from `_currencies_in_use`, which is derived from the very rows being converted; nothing in the function enforces that, and a future caller assembling its own frame would not inherit it. A loud failure needs a `collect()`, which would break the laziness every caller composes on, so this wants either a cheap eager guard at the `DisplayCurrency` boundary or a schema-level guarantee. |
| A8 | A trade and a cash transaction could silently collide on `event_id` | **DONE** (PR C) — found while checking E6's claim that `ibkr_flex_api.md` documented the wrong cash dedup key. The doc said `ibkr:cash:{transactionID}` and `preprocessing._standardize_ibkr_cash_transactions` emitted `ibkr:{transactionID}`, the same shape a `<Trade>` gets — so the app relied on an undocumented IBKR guarantee that the two namespaces never coincide. `main._merge_ledger` dedupes with `.unique(subset="event_id", keep="last")`, so a collision would have dropped one of the two events with no error. The code moved to the doc's key rather than the doc to the code, restoring the convention `ibkr:{transactionID}:fee` already followed. |

## C — speed

| id | item | status |
|----|------|--------|
| C1 | The transactions page filters, sorts and counts in the browser over the whole ledger | **DONE** (PR G) — the SPA half landed and the item is closed. `TransactionsTable` holds one 200-transaction page; `filterPostings`/`matchesFilters` and their thirteen predicates are gone, and `toPostingFilters` is the single translation between the bar's vocabulary and `PostingFilters`. | C2 | The distinct-months list is derived client-side | **DONE** (PR G) — consumed, which is the only thing it was waiting for. `GET /postings/months` has four call sites now: the transactions filter bar, `BudgetPage`, the insights `PeriodFilterBar` and `SpendCurveChart`. | C3 | `trades`' `GET /ledger/export` is unbounded | **DONE** (PR D) — paged onto the shared envelope, `window_unit="event"`, with the SPA walking it through the loop that previously existed only in `accountingApi.ts`. Two corrections to the entry: the paths are **not** identical (`/api/v1/trades/...` against `/api/v1/accounting/...`), which is the per-module namespace doing the job the contract doc says it exists for, not a collision; and the envelope could not simply be imported, because `Page` lived in `accounting.api.api_models` and reaching into it would have been the first real import between the two ledgers. It now lives in `src/http_api`, which neither owns — the independence rule covers their domains, data and write paths, not a wire format. Also closed the reason it drifted: `http-api-contract.md` claimed `tests/api/test_status_codes.py` enforced the contract while that file asserted nothing about pagination, so it now asserts the envelope, the pinned `window_unit`, and clamping rather than rejecting. |
| C4a | `GET /lots`' payload is unbounded | **KEPT, and deliberately not built in PR D** — it was scoped into that PR and then measured, which changed the answer. Both consumers need the whole collection: `LotsTable.tsx` renders all three lists and counts them for its tab labels, aggregating by day in the browser, and `SettingsPage.tsx` exports all three. A paged `/lots` would therefore be walked page by page — and because the FIFO match is recomputed per request, **each page costs another full replay**, so pagination multiplies total work by the page count instead of reducing it. Bounding the payload here is not merely cosmetic, as the original entry said; it is a regression for the only two callers. The honest bound is C4b, or a `symbol`/`year` filter with a UI to drive it, which is its own piece of work. |
| C4b | Closed lots are FIFO-matched by replaying the whole trades ledger on every read | **KEPT** — the recorded fix (persist matched lots) is a PR in its own right, sized next to C1, and four specifics say why it cannot be folded into a bounded-reads sweep. It would be the first materialised derived table in a schema whose `docs/trades/architecture.md` says the ledger is the only source of truth, and the first non-baseline migration. Ten call sites replay; four of them (`valuation`, `cash_sitting`, `charts`) replay *prefixes*, once per event date, which a "lots as of now" table cannot serve. There is no single canonical match to persist: `holdings.lots_table` replays with `net_dividends=settings.tax_enabled` while every other caller takes the default, so `PUT /settings/tax` changes which stored answer is correct. And a sync (`POST /sync-runs` since PR F) deletes and reinserts the whole ledger, and can insert events mid-history, so this needs a permanent wholesale rebuild path rather than a one-time backfill. A stale lot table produces silently wrong tax numbers. **Measured while scoping C4a, and the more urgent half:** `lots_table` is super-linear in ledger size — 0.24 s at 501 events, 1.0 s at 2k, 3.1 s at 5k, **8.0 s at 10k**, with `ledger.replay.replay_ledger` accounting for 7.5 s of the last figure and the per-symbol rollup for 0.05 s. 20x the events costs 35x the time. That is a complexity problem in the replay, not a payload problem, and it is what this item should be judged on. |
| C5 | Dashboards read full history inside their date window | **DROPPED** — owner's call. |
| C6 | `GET /postings` falls off a cliff between `limit=300` and `limit=400` | **DONE** (PR D) — diagnosed before being fixed, and the diagnosis moved the item. The plan flip was real: with no statistics the planner estimated the outer relation at one row, costed the inner side as running once when it ran twenty thousand times, and chose a nested loop whose inner side re-scanned every transaction the tenant owns per posting — `Rows Removed by Join Filter: 7839600`, `Heap Blocks: exact=3237032`, 4.26M buffer hits, 17.7 s against a 15 s bound. But the page size was never the cause: the boundary fell between 300 and 400 on one run and between 200 and 300 on another, because what moves it is the array's effect on a cost estimate. The array is now matched against the indexed `Posting.transaction_id` rather than `Transaction.id`, which the inner join already equates it to — 15.9 s becomes 0.019 s at 300 ids and 16.3 s becomes 0.107 s at 5,000, with or without statistics. `PAGE_LIMIT_MAX` stays at 5,000: the query serves a full page in 0.107 s, so the advertised cap was never the untrue part. The fix also made the page's SQL read proportional to the page rather than the ledger (65 ms fixed and 0.0005 ms per transaction, against 61 ms and 0.021 ms). Why nobody caught it: B5. |
| C7 | `BudgetPage` fetches the whole ledger to render a month picker | **DONE** (PR G) — `usePostingMonths()` replaced the `usePostings()` call, and `BudgetPage` was C2's first consumer. The saving is what the entry said it was and no more: the query key is shared, so it only materialises on a cold cache entered through Budget. |
| C9 | The `categories` staleness trigger invalidates the whole ledger | **KEPT** — raised by PR E, and deliberately left wide there. A category retirement can only change the resolution of postings whose *raw* `category_id` is the retired key: that is exactly `ledger.categorization.apply_category_redirects`' own definition, which rewrites nothing else, so the narrow set is derivable rather than guessed. Left wide in v1 because a wrong narrowing is silently wrong in the direction that matters, and because the same argument applies to `accounts` and `categorization_rules` with different answers — an account *insert* can change resolution (a rule naming an account that did not exist starts matching), so that one cannot be narrowed the same way. Worth doing: a category merge currently costs a full rebuild, 2.0 s at 10k transactions. |
| C8 | The latency gate's bounds are set from pre-B5 figures | **KEPT** — raised by PR D. Every threshold in `test_read_path_latency.py` was derived while the harness measured an unanalyzed database (B5), and the measurements are now replaced but the bounds are not. They can be tightened: the deliberate-break experiment separates cleanly now (healthy 1.0x against broken 3.7x, where before the fix it was 2.6x against 3.6x and indistinguishable), so `MAX_SCALING_FACTOR = 8.0` no longer rejects a page that stops being a page. Deliberately not re-derived from a quiet laptop — CI has historically measured roughly twice the local ratio, and a bound set from local numbers is how a gate starts flapping. Needs a handful of post-B5 CI runs to derive from. |

## D — reliability

| id | item | status |

| D1 | First-login lockout | **DONE** (PR F) — `resolve_current_user_id` provisions on an `external_identities` miss, via a Clerk Backend API call for the email the session token does not carry. Only on a miss (three requests for one provisioned user make one Clerk call, asserted by counting); bounded by a timeout **and** by `retries=None`, since the SDK's default backoff has a one-hour `max_elapsed_time`; fails closed identically on unreachable, erroring, no such user, banned, locked, deprovisioned and no primary email, with only the log distinguishing the one permanent case. Two corrections. The concurrency hazard was **not** a unique violation: two first requests mint different `uuid4`s and `users.email` has no unique constraint, so nothing collides and `ON CONFLICT DO NOTHING` left the loser holding its own orphaned id — silent data loss where a 500 would have been the good outcome. `link_identity` now returns the id actually linked and the loser rolls back to the savepoint and adopts it. And no resurrection is possible: `_deactivate_user` leaves the identity link in place, so a deactivated account still hits the lookup and never reaches provisioning — now tested rather than incidental. Fixed the webhook's own documented orphan case for free, plus `migration/env.py`'s `fileConfig` disabling every application logger in any process that runs migrations. |
| D2 | Sync blocks the request and tracks progress per-process | **DONE** (PR F) — `POST /sync-runs` answers `202` + `Location`, the run is a row in `trades.sync_runs`, `GET` returns it with its result embedded, and a lifespan-owned `ThreadPoolExecutor` does the work. Not `BackgroundTasks`, which is awaited inside the ASGI call and would have held the `202`'s connection for the whole sync and blocked graceful shutdown. Three things beyond the recorded scope: the per-user `threading.Lock` had the identical per-process defect and is now `uq_sync_runs_active_user`, a partial unique index, with a second start answering `409` **carrying a `Location`** to the run in flight; startup sweeps runs a dead process left open, without which one restart mid-sync would wedge that user's slot for ever; and the projection worry was unfounded — the IBKR sync writes only `trades` tables and every staleness trigger is on an `accounting` table, so there is nothing to dirty and no guard test was written for a coupling the architecture forbids. | D5 | Every HTTP request ran under the 600 s background statement timeout | **DONE** (PR F) — raised while planning D2 and taken in the same PR, after the runner. `get_db` called `session_scope(user_id)` and that keyword defaults to `background=True`, because every other caller of it is a cron job or a webhook — so the 15 s per-request bound was never applied and `allow_background_runtime` was a no-op, the bound it raises being already raised. | D4 | Two routers commit twice in one request | **KEPT** — raised by PR E. `POST /tags/{id}/rename` commits inside `repositories.taxonomy.remap_tag_ids` and again in the handler; `DELETE /transfer-rules/{rule_id}` commits the rule removal and again inside `reconcile_and_persist_rule_links`. Pre-existing, and PR E deliberately did not fix it — but it did make it observable through a cache, so it now has a test proving the projection *self-heals*: a drain forced into the window caches the half-applied state, the second commit re-dirties the tables it touches, and the next drain corrects it (`test_a_tag_rename_self_heals_when_a_read_lands_between_its_two_commits` and its rule-delete counterpart). | D3 | Transactions commit inside route handlers | **DROPPED** — 30 `commit()` calls across 11 router modules, but the failure it guards against is now rare (the whole-store version check that used to trigger it routinely is gone) and recoverable. Revisit only after D2, which removes that blocker for free. **PR F confirmed the prediction:** the sync no longer runs in a request at all, so its per-step commits are a property of a background session and constrain nothing about the request transaction. The item stays dropped — the *second* blocker (handlers that catch an error and still return normally) is untouched. |
