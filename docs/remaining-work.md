# Remaining work after the five-PR refactor

The five-PR VISION refactor landed as `v1.2.0` … `v1.7.0`. This is the triaged
backlog that came out of it: the entries in `known-gaps.md`, plus a repo-wide
audit, each one decided rather than left open. Item ids are stable — cite them
in branch names, commits and PR descriptions.

`KEPT` items are planned. `DROPPED` items were considered and consciously
declined, with the reason recorded so nobody re-opens them from an audit
document six months from now.

Two rules for anyone working this list:

**Version bumps follow the policy, not the previous PR.** `PATCH` for anything
whose user-visible behaviour does not change on purpose — which most of this
list is; `MINOR` only for something additive; `MAJOR` only when deploying needs
manual intervention beyond `git pull` and a restart. Say in the commit body
which rule applied. (The policy itself is at `docs/versioning.md`.)

**Check whether it is already handled before building anything.** Read the
neighbouring modules and their docstrings first. A1 and A3c on this list were
both queued as real bugs and both withdrawn on exactly that basis: the machinery
already existed one module over. Docstrings count as documentation. If you
conclude something is broken, state what you checked that would have covered it
and did not.

As of `v1.13.0` every item on this list is `DONE` or `DROPPED`. Nothing here
is planned work any more, so both rules above are written for whoever adds the
next item rather than for whoever picks up the next one.

| C4a | `GET /lots`' payload is unbounded | **DONE** (PR J) — the objection recorded here dissolved rather than being overruled. PR D declined it because each page re-ran a full FIFO replay, so paging multiplied total work by the page count; C4b made that replay linear (3.689 s to 0.039 s at 10,001 events), and at that price a page walk costs less than the one unbounded response did. **Three paged reads rather than one**: `GET /lots/open`, `/lots/closed` and `/lots/symbols`, each on the shared `Page` envelope, because the three collections' lengths are independent and one envelope can only cut one collection. **Cutting by symbol instead was considered and rejected** — it would have bounded nothing, since a single symbol can hold every lot in the ledger; `GET /postings` gets away with a transaction window only because a transaction has a handful of legs. `window_unit` is `lot` for both lot collections (they count the same thing, and a client walking either does identical arithmetic) and `symbol` for the rollup, which is bounded too even though a portfolio holds few symbols: a collection with no page has a size that is somebody's assumption, and each of its rows carries an XIRR solve. | C4b | Closed lots are FIFO-matched by replaying the whole trades ledger on every read | **DROPPED — the recorded fix is retired, and the cost it existed for is fixed instead** (PR J). A `deque` kept in oldest-first order plus a dividend-per-share accumulator (`lots.LotBook`) does the same arithmetic in O(1) amortized per event. Measured on generated ledgers: **0.055 s to 0.0025 s at 501 events, 0.955 s to 0.021 s at 5,001, 3.689 s to 0.039 s at 10,001, and 7.190 s to 0.096 s at 20,001** — 94x at 10k, with scaling against 501 events falling from 66.5x to 15.5x. And `tests/performance/test_replay_scaling.py` asserts the cost ratio between a 2,001-event and a 20,001-event replay, which nothing measured before — the reason a quadratic survived from the first release. **The gate's own premise is the subtle part**: on the obvious ledger shape, where a sell takes a slice proportional to the position, the open-lot book is self-limiting and the *retired* implementation scales at 4.83x for 5x the events, so a gate built on it would have passed the defect it exists to catch.
